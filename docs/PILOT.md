# Invitation pilot: local demonstration and activation decisions

Invitation runtime baseline: merged PR #46, `b595f19a807e333d61c370fbfe9249ff24f71e69`. Handoff main also includes #48 (`69de6d40598a117f29b44b367f18522d679c985d`), confined to the separate offline MPP crate; invitation runtime bytes are unchanged. This is a local handoff, not a deployment release. Existing alpha/site resources, credentials and policies remain unchanged. Public self-service signup, payment fulfillment and commercial trial terms are not enabled.

## Reproduce the complete local journey

Prerequisites: Node 22+, Python 3 with sqlite3, Rust 1.92.0 plus wasm32-unknown-unknown and worker-build 0.8.7. The build scripts select the pinned compiler even if another rustc appears first on PATH. Install development prerequisites from [LOCAL.md](LOCAL.md); then, from the repository:

```sh
npm ci
./scripts/demo-invitation.sh
```

No Cloudflare login or real credentials are needed. The script builds the production artifact, runs the disabled-boundary probes and the integrated local journey, then restores the normal artifact through an EXIT trap. Identities, invitation tokens and HMAC material are generated ephemerally inside the test and never printed. Miniflare uses private disposable SQLite directories. Every outbound receiver is intercepted locally; an unexpected URL is refused. The demo creates no DNS, Worker, namespace, Queue, real grant or payment.

The journey covers enrollment → exact ownership proof → signed scheduled admission → persisted runtime restart → alarm/Queue consumption → v2 HMAC callback. It also checks retry, stable enqueue replay, endpoint revocation before dispatch, cross-project key denial, query immutability and delivery funded before identity/grant expiry. Expected final records contain `status: passed`, 21 disabled-boundary calls, four intercepted callbacks, `accepted_after_identity_grant_expiry: true`, and zero external/live resources. Journey HTTP count varies with bounded status polling (currently about 38; the harness stops above 150). The owned runtime is disposed and its store removed even on failure; do not delete unrelated local saved state to retry.

This restart is real local disposal/recreation over persisted SQLite, not a Cloudflare crash. The separate `npm run test:invitations` suite exercises three actual owned-process SIGKILL boundaries; native denial/lease/funding tests are snapshot simulations. See [verification](VERIFICATION.md), [the gated contract](../contracts/invitation-v1.json), and [integration semantics](INVITATION-DELIVERY.md). Current loopback HTTP examples and the minimal receiver/dedup explanation remain in [QUICKSTART.md](QUICKSTART.md). A source client under separate review is not required by this demo and must not be assumed deployed.

## Decisions needed for a live invitation pilot

Generic public API deployment permission already exists. Do not ask for that again. The following concrete policy/access decisions are still needed; none is supplied by running the local demo.

| Decision | Exact scope to settle |
|---|---|
| Admission duration and allowance | Choose the invitation redemption window, identity/grant admission duration and finite total internal attempt units per invitation. Existing accounting spends one unit per leased attempt and reserves five per new task/redrive; unused units return to an open source grant or retire if closed. Units are not money or a chosen commercial price. Confirm this diagnostic accounting meaning or define a separately reviewed product mapping; do not silently change it. Accepted reservations survive admission expiry. |
| Invitations | Choose the initial recipients/project count and approved private distribution channel. The source uses operator-issued unpredictable tokens with only digests in configuration, not a public issuer. Issuance reserves a lifetime slot before project creation (at most eight projects in this bounded implementation); restart/expiry does not recycle it. Explicitly grant enqueue/read/cancel/redrive and optional manage_destinations. Do not grant broad configure/key administration. No recipient message is sent without authorization. |
| Receiver boundary | Choose an operator-owned dedicated HTTPS host and intended callback URL, plus who installs the ownership response and verifier material. The current operator gate is an exact **host** allowlist; it permits proof requests to paths on that host. It is not an operator-enforced path allowlist. Use a dedicated host whose paths are safe for bounded synthetic POSTs. Each accepted task then pins its exact verified URL/version. Ownership does not prove DNS-rebinding safety; arbitrary customer hosts remain off. |
| Secret storage and access | Approve fresh project-specific callback material and its lifetime, stored as a Cloudflare Worker secret in the dedicated API and securely installed only in the approved receiver/verifier. Bot private keys stay owner-only on the bot; API receives public keys only. No public fixture material, chat/GitHub storage, new provider credential or billing scope. A customer receiver gets **no project Durable Object namespace binding**. Existing alpha receiver's earlier synthetic namespace approval is not permission to bind customer receivers. |
| Resource and rollout manifest | Approve exact new names/IDs and rollback/retention: one separate invitation API Worker, fresh AdmissionRegistry and InvitationProject SQLite namespaces and one runlater-invitation-ready Queue; an additional receiver Worker only if no suitable owned endpoint exists. These are new-mode resources, not reuse of the old alpha namespace. The invitation guard rejects ALPHA_* config, so mixing modes in the retained Worker is not a safe rollout. Review custom-domain switch/rollback and preserve existing services/state until the replacement is verified. No names here are provisioning commands. |
| Monthly cost and pilot lifetime | The existing RunLater budget is US$20/month across retained RunLater resources, not US$20 per test. Confirm current headroom or the precise bounded incremental risk, total traffic/task/publication/CPU/time limits and teardown/retention deadline for this manifest. No plan upgrade or assumed hard cap. Earlier one-campaign risk consent is not unlimited repeat authorization. Billing read permission remains unavailable; do not bypass it. |

Also choose the pilot scheduling horizon and key-retention/closure policy together. The task API can schedule up to 365 days ahead; a short-lived pilot cannot delete its namespace/signing material while accepted work still needs it. Limit the approved pilot inputs/recipients operationally or separately review a narrower enforced horizon. After activation, stop new admission before retirement, drain/cancel under documented policy, preserve accepted-task accounting, then remove only manifest-owned resources. No automatic retirement is implemented by this document.
