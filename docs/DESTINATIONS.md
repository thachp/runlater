# Destination verification: offline source slice

Related issue: [#7](https://github.com/thachp/runlater/issues/7). This increment provides a tenant-bound destination aggregate and an isolated compiled test entrypoint. It does **not** add public registration, a production HTTP route, a binding/migration, or customer task admission. The existing alpha continues to admit only its exact owned receiver. No live resource, credential, identity, grant, deployed route, commercial price or trial term is changed.

## Authority and integration boundary

`src/destinations.rs` owns its state and has no dependency on identity, onboarding, funding or the signed project aggregate. Every operation checks the supplied project against the stored project. The project argument must come from authenticated server context; it is not itself authentication. Before wiring this into the production aggregate, coordinate the interface with onboarding/funding owners. Required integration is: authenticate configure authority for create/prepare/verify/revoke, read authority for get, and enqueue authority for acceptance; atomically commit the destination snapshot with the existing task/funding reservation; use the current authoritative revocation and operator network policy immediately before each new dispatch. Never save this as a separately authoritative side store and claim task acceptance is atomic.

There is deliberately no change to `signed::Project`, its schema, its request permissions, or funding semantics in this PR. The only shared production change extracts the existing bounded transport into `safe_egress.rs`, then calls it from the existing exact-receiver alpha path. No new alpha URL becomes available.

## State, versions and revocation

Each project retains at most 16 immutable endpoint versions across all IDs, at most 16 acceptance snapshots, and three lifetime proof issuances per version. These are conservative source safety ceilings, not a product trial or price. Versions start at 1 and increase consecutively for each endpoint ID. Reusing a version with a different URL conflicts. Each version starts `pending`, becomes `verified` only after a valid bounded proof response, or becomes `revoked`. Updating an endpoint creates a new pending version with a new proof; old accepted tasks keep their selected version/URL.

Revocation is sticky for the entire endpoint ID, including all historical versions. No later version under that ID can undo it. Revocation blocks new admission and the next dispatch/retry of already accepted tasks, and invalidates in-flight verification. It cannot undo an outbound request already started. The destination aggregate does not settle/refund/cancel funding; production integration must use the existing explicit terminal/settlement policy. No silently retargeted accepted tasks, automatic re-verification, budget reset, capacity recycling or background retry is implemented.

Acceptance selection is immutable by tenant/task ID. An identical acceptance replay still returns its original snapshot after revocation or allowlist removal; replay never authorizes another dispatch. Selecting another endpoint/version for the same task conflicts. Dispatch rechecks the selected version's current verified/revoked state and current operator allowlist. `get` and `dispatch` checks are pure. Versioned decoding rejects unknown schemas, tenant confusion and inconsistent version/acceptance/revocation records.

## Bounded ownership protocol

1. The authenticated owner requests a proof for a pending endpoint version. The adapter generates 32 secure random bytes with Workers Web Crypto `getRandomValues`. Core tests use labelled deterministic fixture nonces. Issuance consumes one of three lifetime slots; one unexpired proof per version can exist. The 60-second TTL is fixed source configuration, independent of task/trial duration.
2. Return the owner the exact UTF-8 response to configure on their endpoint:

   `RunLater destination proof v1\n` followed by compact JSON `[1, project_id, endpoint_id, endpoint_version, exact_url, lifetime_attempt_number, expires_at_ms, nonce_hex]`.

   Store only its SHA-256 digest and expiry, plus a one-use fetch lease. Do not log the nonce, expected response or raw receiver response. The response is not stored in the durable snapshot or returned by normal queries.
3. Once the owner configures the endpoint, verification acquires and **durably persists** the one-use lease before Fetch. It POSTs to the exact registered URL with `text/plain; charset=utf-8`, no customer headers, cookies, delivery signatures or credentials. The request body is `RunLater destination verification v1\n` plus compact JSON `[project_id, endpoint_id, endpoint_version, proof_digest, expires_at_ms]`. It omits the secret nonce/expected response. An endpoint that simply reflects the request cannot pass.
4. Only HTTP 200 with the exact expected response bytes passes, using constant-time digest comparison. Reload authoritative state after network I/O; check tenant, version, URL, lease, current policy and expiry again before committing verified. The completion boundary is strictly before expiry. Responses for another tenant/version/proof fail. A completion is one-use even on failure. Replaying verified completion cannot fetch again.

Lost prepare response: wait for expiry, then issue another bounded proof. Interrupted Fetch after durable lease: a duplicate verification conflicts; it does not send again. After expiry, another issuance can use a remaining slot. Failures never refund the lifetime counter. A superseded attempt cannot complete a newer proof. A successful response does not override revocation committed during I/O. Clock regression fails closed.

The endpoint owner must deliberately configure the response. Possession of a callback key, a client-supplied response, a redirect, an echo handler, a non-200 status or a previously returned response is insufficient. This proves only that the configured endpoint can return the current tenant/version-bound secret. It is not proof of legal domain ownership, human identity, independent tenant identity or network safety.

## Egress and SSRF boundary

Ownership **does not establish SSRF safety or DNS-rebinding resistance**. `EgressPolicy` is a separately trusted operator input, closed by default. Only explicitly approved exact DNS hostnames are accepted, with canonical HTTPS URLs up to 256 bytes. Wildcards, suffix matching, IP literals (including encoded forms), alternate/default-explicit ports, userinfo, query/fragment, normalized URL aliases and caller-selected hosts outside the policy fail. DNS is not resolved or pinned by these URL checks. Operators must approve only controlled hosts whose routing they trust; neither this PR nor local interception proves cloud DNS/TLS safety. Arbitrary customer hosts remain disabled pending an independently verified runtime egress design.

Proof and alpha delivery call the **same** transport implementation: POST; `RequestRedirect::Manual` and rejection of every 3xx without following its Location; one 3,000 ms abort deadline covering headers and the complete body; at most 2,048 response-header bytes, 1,024 body bytes and 32 chunks; at most 1,024 request-body bytes. The abort controller runs on every exit. Header/body/redirect failures are rejected; transport or body-stream uncertainty cannot verify. Raw response bytes are transient and discarded after comparison/category selection. The alpha keeps its existing bounded receiver error categories and callback-v2 signing behavior.

Cloudflare references consulted: [Request redirect behavior](https://developers.cloudflare.com/workers/runtime-apis/request/), [Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), [Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/), and [SQLite storage atomicity](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/). In particular, Workers defaults new requests to following redirects; `manual` must be explicit. Synchronous SQL writes without intervening awaits are atomic. Pinned workers-rs 0.8.7 source/types and Rust 1.92.0 are used.

## Verification and honest limits

`tests/destinations.rs` covers lifecycle/isolation, URL aliases and closed policy, reflection rejection, one-use leases/completion, context substitution, exact expiry, clock rollback, lifetime failure/interruption caps, immutable acceptance/version selection, sticky revocation, host-policy removal, query purity, redaction and versioned decoding.

`npm run test:destinations` builds the real Rust/Wasm with the **isolated** `destination-tests` feature. The disposable local Miniflare/workerd fixture has two fixed tenant objects and SQLite snapshots; all outbound Fetch is intercepted locally. It exercises the source protocol, redirect/header/body/chunk rejection, header and body deadlines, stream failure, replay/no-second-Fetch, revocation interleaving during Fetch, process disposal/restart and persistence, tenant isolation and immutable acceptance snapshots. Expiry uses a deterministic fixture clock rather than a real 60-second wait. Process disposal is an actual local workerd shutdown/restart, not a cloud crash/failure claim. The test fixture supplies receiver responses through its own in-memory owner configuration and never makes external calls.

The test-only entrypoint has no production authentication contract and must never be deployed. It requires a fixture service binding, cannot be combined with any other runtime feature, and is absent from normal and production artifacts. The script restores the default build and checks for fixture markers. Existing compiled alpha-delivery tests must also pass because the shared transport changed. These are local proofs; production route integration, durable atomic task/funding acceptance, live DNS/TLS/rebinding defenses, deployed receiver proof, account billing and cloud interruption evidence remain separate review/activation work.
