# Production boundary and operator-approved possession enrollment — source only

This is a separate compiled `production` profile, not an activated service or complete production task API. It excludes the local/staging task runtime and cannot compile with `staging` or `runtime-tests`. Default/staging builds retain their reviewed behavior. No Cloudflare binding, namespace, secret, real operator identity, domain or deployment is provisioned here.

The production entrypoint accepts only HTTPS api.runlater.io. Missing explicit configuration fails 503; local/staging/test environment bindings, bootstrap API_KEY_HASHES and task/Queue bindings fail closed even when their flag value is false. All Authorization headers are rejected: public local bearer tokens, staged tokens and newly invented bearer tokens grant nothing. Test/staging headers and forged x-tenant context are rejected. No in-process fixture success path exists. Every task/key/payment/unknown route returns 503 with task_accepted=false. GET /health describes enrollment plus signed-read/configuration mode, unavailable task API and disabled outbound delivery; it does not report task readiness.

## Configuration and durable catalog

Future activation would require ALPHA_ENROLLMENT=operator-approved, an ALPHA_PROJECT_POLICIES JSON array and an IDENTITIES SQLite Durable Object binding to exported ProjectIdentity. There are deliberately no default policies, public-key fixtures, bootstrap credentials or production deployment config. Actual public-key enrollment/configuration and any persistent production credentials need specific approval. Offline runtime tests generate ephemeral Node test keypairs held only in memory and use local Miniflare bindings; they are not real operator credentials.

The server-owned policy has project_id, positive immutable revision, revoked, approvals and revoked_keys. Each approval binds a lowercase 64-hex Ed25519 public key, task/configure permissions and an absolute expiry. ManageKeys/purchase authority is not granted. Limits are 8 configured projects, 4096 policy bytes, 8 approvals per project and a conservative 256 combined history/approval/revocation slot budget. Approval expiry must be positive and at most 30 days ahead of command time; these are security bounds, not commercial trial defaults. No entitlement, trial allowance, funding or payment is issued.

A project catalog durably binds its project name. Same-revision content changes and lower revisions conflict. Higher policy revisions invalidate older challenges. Removing an approved key or listing it in revoked_keys permanently revokes that key after the revision is durably applied; later policy re-addition cannot revive it. Project revoked is also sticky. Enrolled scopes/expiry cannot be expanded by policy changes: effective authority is the intersection with current approval and the original enrollment. Rotation requires a newly approved key. Catalog history is not silently purged; reaching the history cap fails closed.

POST /v1/identity/sync accepts only `{project_id}` and applies the already server-configured policy, never caller-supplied policy/grants. It issues no authority and is safe to invoke without a proof. Operator rollout must confirm durable sync before treating a revocation as recorded or rolling back configuration. Removing a project entirely from configuration disables routing; it is not itself a permanent project revocation command. Persist revoked=true before removal when permanent revocation is intended. Storage loss/deletion and operator configuration integrity remain operational trust boundaries.

## Exact proof protocol v1

Ed25519 is implemented by pinned ed25519-dalek 2.2.0 using verify_strict and weak-key rejection; the algorithm is described in [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032). The application message framing below is RunLater-owned, not a new signature algorithm or an industry enrollment standard. [Library verification reference](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict).

POST /v1/identity/challenges accepts exactly `{project_id,public_key}`. The key must already be operator-approved, active and unenrolled. The server obtains 32 random bytes from Workers WebCrypto getRandomValues, encodes them as lowercase hex, and returns the challenge, challenge_id and canonical_utf8. Proof expiry is the earlier of issue time+300000 ms and the approval expiry. No origin, purpose, scopes, nonce or timestamp is caller-selectable.

Exact signed bytes are UTF-8 `RunLater enrollment proof v1\n` followed by a compact JSON array, no trailing newline:

```
[version,origin,purpose,project_id,public_key,nonce,issued_at_ms,expires_at_ms,policy_revision,policy_hash,permissions,identity_expires_at_ms]
```

version is 1; origin is https://api.runlater.io; purpose is operator_alpha_enrollment. Keys/nonces/hashes are lowercase hex. IDs and enum strings are restricted ASCII. Integers use decimal JSON encoding. Permissions serialize in the existing enum order: enqueue, read, cancel, redrive, configure. The server's canonical_utf8 is the exact message; clients must independently check expected origin/purpose/project/key/scopes/expiry before signing it. This is not RFC 8785 JSON canonicalization and arbitrary object encodings are not accepted. challenge_id is lowercase SHA256 of those exact bytes. policy_hash binds serde's fixed policy representation and revision; reordered/changed policy content requires a new revision.

POST /v1/identity/enroll accepts exactly `{project_id,challenge_id,signature}` with a 128-hex Ed25519 signature. It loads the stored challenge, checks current policy/project/expiry/revocation and verifies the exact stored bytes. It never accepts a client-supplied replacement challenge. Verification, one-use consume and scoped enrollment happen synchronously, then commit together in one atomic SQLite snapshot upsert with no intervening await. The monotonic server policy is persisted first as a separate configuration transition. A concurrent replay yields one 201 and one 409. An unknown/expired challenge yields 410; three invalid proofs lock the challenge. No signatures, private keys or reusable bearer credentials are persisted or returned.

At most 64 challenge rows per project and 8 per key are retained within the five-minute window, including consumed/failed rows. Expired rows are pruned on a subsequent challenge command; bounded storage needs no polling/alarm loop. Commands record a clock high-water mark and reject regression. Pure authorization lookup clamps to the last recorded command time; it does not advance time or authenticate request possession. The helper is not exposed as an unsigned task authorization route.

Request bodies are limited to 2048 bytes,32 chunks and a five-second read window. Policies are server-controlled, not request data. Responses use fixed error categories, with no request/credential/body logging. Source bounds do not constitute a global ingress/billing cap or proof of abuse resistance; operator-approved alpha enrollment does not prove human identity, Sybil prevention or entitlement.

## Tests and remaining integration

Native tests cover an RFC 8032 verification vector, strict weak-key rejection, every signed context field, invalid/replayed/expired/cross-project proofs, concurrent-safe transition semantics, clock regression, scope intersection, immutable revisions, sticky key/project revocation, TTL/capacity and pure queries. The compiled local Worker/SQLite suite verifies actual WebCrypto nonces and Rust verification of Node signatures, concurrent single-use submissions, clean restart, policy sync/revocation, expiry and production-mode separation. No cloud or real identity was used. Wrappers restore the default artifact and check separation markers.

This proves enrollment/catalog plumbing, not functional task authentication. The next increment adds [signed reads and configuration](SIGNED-REQUESTS.md).
