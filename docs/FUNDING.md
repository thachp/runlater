# Finite operator-alpha funding (source-only)

This increment adds internal attempt accounting and signed task read/cancel/enqueue/redrive application paths to the authoritative project aggregate. It does not activate a hosted API, credits/payment product, registered destination service, Queue driver or callback delivery. Production supplies no admission context: fresh enqueue/redrive fails with `503 delivery_not_ready`, even for valid enrolled keys. Existing funded task replay/cancel is separate from fresh acceptance. The local default prototype API is unchanged.

## Accounting and atomicity

Unit policy v1 reserves five internal attempt units at new task acceptance, matching the finite five-attempt budget. Units have no currency value or chosen commercial price/trial terms. A committed lease spends one unit once per fence. Duplicate references and stale outcomes cannot spend or refund twice. Uncertain effects remain spent. Scheduling and admission-grant expiry do not remove accepted reservations. Redrive creates a distinct funded task; an identical redrive retry resolves its existing child first.

The project SQLite snapshot holds identity policy, signed nonce guards, task ledger and funding. Validation and effect run on a clone with no non-storage await; one synchronous row replacement ([SQLite storage semantics](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)) persists successful task/reservation/nonce changes. Failed admission leaves task, funding and nonce unchanged. Latest identity policy and monotonic policy time may still be persisted to enforce revocation. This bounded implementation is not a general distributed transaction proof.

A grant has immutable ID, amount and admission expiry. Revisions cannot change/replenish an existing grant. Replays, restart, rollback and removed revocations cannot reopen a closed grant. Expiry/revocation retires only available units, preserving reservations. Available + reserved + spent + retired equals original total. At terminal settlement, unused units return to the **open source grant**, even if another grant is selected for new admission; otherwise they retire. A durable immutable settlement records disposition, spent/unused units and terminal/settlement times. Repeated cancel or settlement cannot refill balances. This is internal resource accounting, not a commercial refund promise.

Task/reservation/idempotency evidence survives the entire active lifetime plus 30 days after terminal state. Maintenance purges settled reservations only with their terminal task; grant history remains to prevent reuse/replenishment. This does not use the 24-hour configuration receipt window. Limits: 32 grant identities/revocations, 1,000 reservations/project, JavaScript-safe counters, existing ledger quotas and signed gateway's 2 KiB body limit. More history requires an explicitly reviewed migration, not dropping grant tombstones. Snapshot v2 requires funding data; old unfunded v1 snapshots migrate in memory without writing on GET.

## Local evidence and limits

Run `npm run test:funding`. A mutually exclusive `funding-tests` build requires HTTP loopback plus private `TEST_FUNDING_CONTROL` service binding; without it requests fail closed. It cannot combine with production, staging or runtime-test builds. Its private DO methods model claim/outcome accounting; they do not invoke Queue or HTTP delivery. Production/default artifacts are checked for absence of fixture hooks, and the wrapper restores the default artifact.

Compiled Worker/SQLite tests cover concurrent last-budget admission, one reservation, process disposal/restart and lost-response replay, read immutability, tenant separation, cancellation, duplicate logical claims, uncertain outcome cost, redrive and expiry replay, policy rollback/spec conflict, sticky expiry and conservation. Native tests additionally exercise long scheduling, all five retries, stale fencing, retention and clock rollback. Tests use ephemeral local signing identities and owner-marked disposable stores; no real customer/provider data.

The `registered:<id>` syntax in the model is **not endpoint verification**. Production cannot use it to admit tasks yet. No public grant-activation route or environment fallback exists. No automatic provisioning, monetary debits, production credentials or live effects are included.
