# Guarded API releases (not enabled)

`release-api.yml` builds on a GitHub runner after **Local prototype checks** passes for a push to main. It deploys only the current main SHA, serializes releases without cancelling an in-flight mutation, and uses the `runlater-public-api` environment. Fork/PR runs cannot release. Normal releases upload one version, recheck active deployment/settings for drift, then promote that exact version. There are no automatic retries, infrastructure creation, migrations, domain changes, secret issuance or rollback.

This bypasses the Mac connector/IPC round trips that exhausted the supervised provisioning window. It does **not** fix or replace first provisioning: the public Worker currently does not exist. The existing `runlater-alpha-api` is a different application/profile and is deliberately rejected. Its settings URL must not be used as the beta release target. Keep alpha and accepted work intact.

The existing alpha has no Workers Builds triggers (read-only API inspection). Native Workers Builds is another option, but requires a GitHub integration grant and deploy-token setup and runs on push independently of this repository's long integration suite. Do not configure both systems. This implementation chooses Actions so the actual required CI finishes before release.

## Activation prerequisites — separate approval required

1. Review/merge this source, and protect main: require PR review, passing `rust-and-hosts` and other applicable checks, block force pushes/deletion, restrict bypass. Main was unprotected at assessment. Workflow code cannot enforce repository administration settings. Add CODEOWNERS/review policy for workflows, release scripts, lockfiles and deployment config as appropriate.
2. Create the `runlater-public-api` GitHub environment, main-only deployment branch restriction, required reviewer and prevent self review. If the repository plan does not support those protections, do not enable releases; select an equivalent independently reviewed approval gate first. No repository settings were changed by this patch.
3. Specifically authorize a **new persistent Cloudflare CI API token**, stored only in that environment's `CLOUDFLARE_API_TOKEN`. Minimum current documented scope: **Workers Editor restricted to the existing `runlater-public-api` Worker**, plus **Queues Read on the selected RunLater account**. Pinned Wrangler4.154.0 lists Queues by name during `preUploadApiChecks` even for versions upload; it does not create them. Queue metadata listing is account-scoped. No Account Settings Read is needed with the explicit account ID; no DNS, routes, billing, Queue Write, token-management or product-wide Workers Admin permission is requested. Current Cloudflare roles support individual Worker scopes; the legacy Workers Scripts Edit permission is broader and must not be silently substituted. Editor can update code/settings/secrets for this Worker, and malicious code could use its existing data bindings or expose its callback master; it is persistent privileged access even with per-Worker scope. Set a short expiry and rotate/revoke explicitly. Existing local OAuth credentials must not be copied to GitHub. Do not create this token without specific consent. A per-Worker token cannot be created for a nonexistent Worker; first provisioning remains separate. If the account/token UI cannot express the narrow scope, stop and report rather than expand permissions.
4. Complete separately approved first provisioning, master-secret installation, verified bindings/consumer/rate limits, and supervised public cutover. This workflow never provisions the beta or retries the failed launch. Preserve the existing fixed beta profile, release ID, namespace identities, revocations and key validity. A normal source release must not reset an admission/grant cohort. Migration/schema/policy changes require their own review and release procedure.
5. In the protected environment configure nonsecret variables:
   - `RUNLATER_RELEASE_CONFIG`: strict JSON of the approved **existing-resource** Wrangler profile. Adapt `beta/wrangler.example.jsonc`: main `build/worker/shim.mjs`, remove `$schema`, `build`, `migrations`, and Queue `consumers`. Keep all required bindings, CPU50, observability off, previews/workers.dev off and strict-public fetch. Set the actual immutable approved `PUBLIC_BETA_PROFILE`, existing revocations and `PUBLIC_BETA_ENABLED`=`operator-approved`. Never include secrets. Consumers/routes are separately managed and unchanged by version promotion.
   - `RUNLATER_RELEASE_APPROVAL`: JSON `{ "worker":"runlater-public-api", "account_id":"<approved account>", "config_sha256":"<canonical config hash>", "settings_sha256":"<canonical existing provider settings hash>" }`. Obtain provider settings with an authorized read; never export secret values. `digest` in `scripts/api-release.mjs` sorts object keys recursively; hash the parsed JSON `result` for `/workers/scripts/runlater-public-api/settings`. Hashes are drift detectors, not a substitute for reviewing configuration. Refresh only after reviewing an intentional provider change. No real profile or account ID is committed here.
   - Initially keep `RUNLATER_RELEASE_ENABLED` unset. Only set to `true` after exact activation approval/protections/baseline verification. Separately set repository variable `RUNLATER_AUTODEPLOY_ENABLED` to `true` to permit the job trigger. The execution gate is the distinct environment variable `RUNLATER_RELEASE_ENABLED`; never define that name at repository/organization scope. GitHub evaluates job `if` before environment variables are available. Setting only the repository trigger flag cannot satisfy the script gate. Both flags must be deliberately enabled.
6. Verify first deployment with supervision. Provider upload/settings/version behavior has not been exercised using a new CI token. `versions upload --strict` and settings hashes intentionally fail closed if Wrangler changes unexpected metadata. Do not weaken checks to make a first run pass. Preview URLs must remain absent. Recheck `https://api.runlater.io/health` and truthful beta availability after promotion, with no signup/task traffic. Publish nonsecret release/key validity metadata separately.

## Failure, drift and rollback

After promotion, one bounded GET checks public `/health` returns200; this is not a signup/callback proof. Each provider read has a 15-second deadline; each Wrangler child has 120 seconds, the job 20 minutes. These are runner bounds, not Cloudflare billing hard caps. Upload or promotion timeout can have executed remotely. Inspect version/deployment history before retry, record the exact uploaded version, and preserve all DO/Queue state and secrets. A staged but unpromoted version may remain after a guard failure. Never automatically delete it or reset resources. Provider external administrators can race the final check; serialize all releases operationally as well.

Rollback means explicitly promote a reviewed prior compatible Worker version after checking state-schema compatibility; no automatic data rollback and no DNS remap. An old binary may be unsafe after a migration. Keep `RUNLATER_RELEASE_ENABLED` false during investigation. Rotating secrets or changing revocations/profile/settings intentionally invalidates the pinned baseline until reviewed. No automatic cohort refill, key generation, paid logging or resource provisioning occurs.

## Local verification

Tests never contact Cloudflare. No end-to-end CI credential/deployment success is claimed until activation.
