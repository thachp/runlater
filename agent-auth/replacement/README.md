# Replacement candidate: Better Auth Agent Auth

This is the source-only replacement path requested after PR82/83. It is not a
parallel production auth service and does not extend the lifetime of old OAuth.
The candidate entry point imports Better Auth directly and never imports
`mcp/oauth.mjs` or the bespoke consent/transaction/provider stack. When selected
and explicitly configured, it returns 410 for the old `/authorize`, `/oauth/token`,
OAuth metadata, `/mcp`, `/sse` and `/messages` routes. It serves Agent Auth discovery
and only the allowlisted Agent Auth endpoints. It does **not** pretend a signed
Agent Auth JWT is an OAuth bearer grant.

The existing production entry point/configuration is unchanged. This candidate
has no deploy command, migration command against a real database, runtime resource
identifier, route binding, API key, or production credential. Its gate is off
unless explicitly set; merge alone does not select it. The real self-hosted
Better Auth server requires a future operator-provided session secret, not a
Better Auth cloud API key. No secret is requested or accessed by this work.

## Executable evidence

```sh
cd agent-auth
npm ci
npm run test:replacement
npm run schema:replacement
```

Tests bundle the actual `better-auth@1.7.14` and `@better-auth/agent-auth@0.6.2`
server into local workerd with nodejs_compat, a real local D1 binding and a SQLite
DO. No network egress is permitted by the harness. `schema.sql` is generated by
Better Auth's actual `getMigrations().compileMigrations()` against empty local
SQLite; it is additive to a **new auth database**, not a script for modifying the
existing project/DO data. No schema or credential is inferred from the old store.

Autonomous registration has no human account step and uses inline public keys.
Clients manage their own host/agent private keys and sign short-lived requests.
Default capability `connection_status` only reports that explicit project linking
is required. It cannot provision, schedule, inspect another project, copy a trial,
reset quota or infer project control from the new host key. Scheduling is absent,
rather than secretly enabled with a substitute budget.

The fixed, bounded `AgentAuthReplacement` DO serializes full auth operations,
including queued lifecycle promises and storage sync. Better Auth's split replay
`has`/`add` operations therefore share one serialized owner and a persistent
SQLite secondary store. Its rate limiter uses the real 1.7.14 required atomic
`SecondaryStorage.increment`. This is not a claim that generic D1/KV get/set is
atomic. A different DO routing name, direct calls bypassing it, or another server
instance sharing D1 would invalidate the design.

The identity admission ledger allows ten lifetime host keys and four lifetime
agents per key. These are **auth enrollment bounds**, not the existing API's ten
project slots. Reservations survive failed/partial registration, revocation and
restart. An immutable public-key-to-host mapping and tombstone survive the
plugin's public-key clearing on real signed `/host/revoke`; guarded JSON queries
avoid malformed-JSON failures on cleared keys. Active host/grant DB checks prevent
existing active agents from bypassing host revocation and prevent expired grants
from being auto-granted again. Remote JWKS, dynamic account linking, signup,
password sessions, arbitrary capabilities and batch execution are not exposed.

Background tasks are drained and uncaught task rejection returns unavailable.
Some upstream tasks catch their own D1 errors, so ordering is proven but arbitrary
D1 failure/revocation fault recovery is not. A durable outbox/reconciliation pass
for partial lifecycle writes is still needed before rollout. Host-signed revoke
is available when an expired agent grant cannot self-revoke. Request bodies,
chunks, headers, queued auth operations and secondary-store capacity are bounded.

## Meaning of removing bespoke authentication

Remove the gateway OAuth provider/consent/token endpoints from the selected
runtime entry point. Do not remove the API's signing verification, project
ownership checks, trial descriptors, revocation enforcement or the delivery
engine: these are the existing authority and task execution boundary. Deleting
those would invalidate queued tasks and expose projects, not merely replace login.

`migration.mjs` provides a pure cutover inventory gate. It accepts redacted
identity/task/quota/revocation state digests and hashed grant identifiers, rejects
credential fields, preserves original project IDs/expiry/remaining attempt units
and all lifetime slots, and creates zero new projects/capability grants. It rejects
state drift and attempts to alter the plan to reset budgets or delete state. It
never reads production, exports tokens or writes either store. Authoritative
inventory extraction and explicit two-sided project-control linking still need
implementation and action-time authorization to touch live state.

OAuth grants and refresh tokens cannot be converted into possession of a new
host/agent private key. An existing user must explicitly reconnect with an Agent
Auth client, prove control of the old project/grant through an authenticated
migration bridge, and sign a challenge with the new identity. Link exactly the
original project/namespace/descriptor and retain its expiry, consumed budget and
revocation tombstones. A valid OAuth client token alone must not mint independent
new API signing authority; no such conversion is implemented here. Lost-key
recovery also needs an enrolled independent control proof, not a fresh trial.

## Cutover sequence and remaining blockers

1. Freeze a redacted authoritative inventory of all owner/trial slots, tasks,
   identities, quotas, revocations and grants. Review the replacement plan and
   client reconnection policy. Do not reset, delete or rename existing state.
2. Add a reviewed new D1 auth database and SQLite DO binding, session secret and
   migration under separate action-time approval. Test D1 fault injection,
   partial registration/revocation recovery, cold starts, queue/storage bounds and
   authenticated key lifecycle. This PR provisions none of them.
3. Implement the explicit control-linking bridge and one shared trial admission
   path using the existing API quota/project authority, release signing trust,
   seven-day expiry, 100 attempt units and lifetime cap. Do not use the fixture
   debit ledger as an actual second budget. Add `http_schedule` only through the
   existing signed API client after this bridge passes cross-store fault tests.
4. Validate an actual Agent Auth client/MCP bridge and required capability/schema
   semantics. The official `@auth/agent` SDK manages keys; no native MCPJam support
   was established. Conventional OAuth MCP clients will receive 410 after cutover.
   Removing `/mcp` does not make Agent Auth an MCP transport. A local Agent Auth
   MCP client bridge or explicit SDK integration is required to call capabilities.
5. With explicit production cutover approval, select the replacement entry point,
   stop old OAuth issuance/refresh and return protocol migration errors. Retain
   old grant records, quota/identity/task state and requested revocation cleanup.
   Retire old runtime files/dependency only after import-graph and rollback review;
   shared `oauth-consent.mjs` scope constants currently also serve the old MCP
   transport, so deleting every oauth-prefixed file blindly is unsafe.
6. Rollback selects the previous entry/version while preserving new identity
   records, old state, quota and tombstones. Decide whether newly issued Agent
   Auth identities are suspended; do not restore revoked grants or issue trials
   on reconnect. Existing tasks keep their original identities and deadlines.

This is a bounded real-package replacement **candidate**, not a completed usable
RunLater scheduling cutover. The replacement is mechanically real (old routes
retired, real Agent Auth/D1 server) while the authority migration remains blocked
by explicit control-linking/admission and fault recovery requirements. None can
be solved safely by importing old credentials or guessing client compatibility.

The separate Next.js PR84 covers landing/docs only; this backend is independent
of Next.js and changes no shared web/auth routes or deployment architecture.
Existing Agent Auth CI integration is still pending its separately recorded
workflow-writing authorization; no alternate publishing path is attempted here.
