PUBLIC FREE BETA / V1

A task for your
agent’s future self.

Schedule one-time HTTP tasks, inspect attempts, and recover safely from uncertain results. Start by understanding what’s available.

Public HTTPS and no-account Connect are enabled. Connect through OAuth and explicitly provision a finite trial before scheduling. The beta is finite: seven days, 100 attempt credits and 16 lifetime tasks per project, subject to remaining capacity in the 10 lifetime project slots. Payments are disabled. Existing owner-key receiver integration remains available separately.

CONNECT / RELEASE GUIDE

Your endpoint.
Your application’s next step.

In a compatible OAuth MCP client, add https://mcp.runlater.io/mcp (Streamable HTTP), or https://mcp.runlater.io/sse for legacy SSE. Verify the client, return destination and requested permissions, including http_schedule. Choose Start free agent project. No account or private-key generation is required for this new-project path. Support in a particular commercial chatbot UI requires separate verification.

The client stores OAuth credentials privately. Connecting and reading status do not allocate a project. Explicitly request provision_trial({"accept_finite_trial":true}) to allocate this connection’s one trial, then inspect trial_status. The seven-day deadline starts at consent. Reconnecting or refreshing never resets quota or expiry; never create another identity to bypass a limit.

Ask the agent to invoke schedule_http_request only for your authorized endpoint and intended action. Replace the illustrative timestamp with your selected future UTC milliseconds within trial expiry:

MCP TOOL ARGUMENTS · EXPLICIT SCHEDULING
{
  "url": "https://app.example.com/events",
  "payload": {"action": "follow_up"},
  "run_at_ms": 1800000000000,
  "operation_key": "follow_up_01",
  "idempotency_key": "task_follow_up_01"
}

No RunLater receiver, ownership proof or completion callback is required for this general path. The endpoint must accept POST application/json without private authentication or custom headers. HTTPS on port 443 and a canonical public DNS hostname are required; IP literals, userinfo, fragments and followed redirects are unsupported. Serialized JSON payloads are limited to 1,024 UTF-8 bytes. Never paste API keys, secret webhook paths/query strings or credentials into model-visible tool input.

The API route is POST /v1/http/tasks; its JSON body has the first four fields above and its Idempotency-Key header supplies the fifth. This is an authenticated trial route used by the gateway, not an unauthenticated curl endpoint. Existing owner grants do not gain http_schedule automatically.

Keep both stable keys and identical input after uncertainty; inspect the same project before any deliberate retry. General delivery sends the operation key as the downstream Idempotency-Key. Your application must durably deduplicate it: task-level delivery is at least once, and a timeout may follow an actual effect. HTTP success does not prove business completion or wake an arbitrary chatbot conversation.

01 / GET STARTED

Optional owner-key integration.

Start with two read-only checks. Health declares the mode; capacity reports whether another project can register.

PUBLIC · READ ONLY
curl --fail-with-body https://api.runlater.io/health
curl --fail-with-body https://api.runlater.io/v1/beta

For this optional owner-key path, expect mode: public_free_beta, payments: false and receiver: workers.dev_only. That receiver field describes the registered beta path; it does not report general HTTPS availability. MCP health and OAuth discovery separately expose the general profile. Capacity can change; a health200 is not an enrollment or delivery guarantee.

Keep your private key local.

Use Node22+ and the repository client. Generate an Ed25519 key locally, store it in an owner-only directory, and never upload its private bytes. No invitation or payment is required.

LOCAL TERMINAL · PRIVATE OUTPUT FILE
git clone https://github.com/thachp/runlater.git
cd runlater
mkdir -p private && chmod 700 private
node --input-type=module -e 'import {generateKeyPairSync} from "node:crypto"; import {writeFileSync} from "node:fs"; const {privateKey}=generateKeyPairSync("ed25519"); writeFileSync("private/bot.pem", privateKey.export({type:"pkcs8",format:"pem"}), {flag:"wx",mode:0o600});'

The repository ignores /private/; never force-add its keys, receipts, callback material or proofs. Key creation refuses to replace an existing key: retain it for recovery.

The following local module deliberately registers one bot under the fixed beta terms. The release metadata contains the actual release ID; do not invent it.

NODE MODULE · EXPLICIT PROJECT ALLOCATION
import fs from 'node:fs';
import {PublicBetaClientV1, PUBLIC_BETA_TERMS, loadOwnerKey, writeOwnerJson}
  from './examples/public-beta-client.v1.mjs';
const release = JSON.parse(fs.readFileSync('./discovery/public-beta-release.v1.json'));
const client = new PublicBetaClientV1({privateKey:loadOwnerKey('./private/bot.pem'),
  releaseId:release.release_id, fetchImpl:globalThis.fetch});
const status = await client.status();
if (!status.registration_open || status.remaining_projects < 1) throw Error('Beta full or closed');
const offer = await client.challenge();
const receipt = await client.complete(offer, PUBLIC_BETA_TERMS);
writeOwnerJson('./private/receipt.json', receipt);

Prepare your receiver before requesting proof.

Deploy the receiver example on an exact worker.account.workers.dev HTTPS host in your own Cloudflare account. Retrieve only your project’s callback key and combine it with the published nonsecret key-validity metadata. Install callback material privately as CALLBACK_KEYS; never put it in public vars, source or logs.

Then create the destination, prepare a proof, privately install its exact JSON as OWNERSHIP_PROOF and verify. Proofs last five minutes, with three lifetime issuances per endpoint version. There is no public setup endpoint. Ownership is separate from network safety; custom domains, IP literals, redirects and arbitrary hosts remain unsupported.

Follow the complete registration → receiver → proof → task walkthrough, including the receiver-policy construction. After verification, deliberately schedule:

VERIFIED RECEIVER REQUIRED · FUNDED ADMISSION
const accepted = await client.enqueue({endpoint_id:verified.endpoint_id,
  body:'{"hello":"later"}', operation_key:'follow_up_01',
  run_at_ms:yourSelectedUtcMilliseconds}, 'task_follow_up_01');
const task = await client.task(accepted.result.id);

Schedule within your receipt’s expiry. Acceptance is durable task creation, not callback success. After uncertain admission, keep the exact key, body, operation key and schedule for a deliberate retry. Recover the same identity with client.recover(); a new key must not be used to claim a replacement trial. The client has no automatic retry, polling or payment loop.

02 / AUTHENTICATION

Optional owner-key API authentication.

The optional owner-key API path uses a RunLater-owned Ed25519 envelope binding origin, project, public key, method, path, empty query, exact body digest, idempotency key, timestamps and nonce. This owner-key API flow does not use bearer tokens. Hosted Connect separately uses OAuth credentials and agent-held trial authority; see the Connect guide for http_schedule. The private key never leaves your client.

OperationRequired owner-key authority
Create / redrive taskCurrent enrolled key, enqueue / redrive scope, unexpired finite grant and available registered destination
Inspect taskRead scope; identical signed reads can replay within their validity window
Cancel taskCancel scope; already in-flight effects remain uncertain
Destination and callback-key managementmanage_destinations scope; proof required before new task acceptance

Signatures have a maximum 60-second validity window and no implicit clock-skew allowance. Use current trusted UTC time. Query parameters are unsupported. The public-beta contract describes these routes and exact framing. Callback HMAC-v2 keys are separate from client request keys.

03 / TASK LIFECYCLE

Accepted means durable. Delivered is later.

  1. Accept: task, idempotency identity, destination snapshot and finite retry reservation commit together in the authoritative project ledger.
  2. Wait and claim: alarms and Queue references wake eligible work. A fenced lease prevents duplicate transport references from creating a new simultaneous claim.
  3. Attempt: general HTTPS receives JSON with the operation key as Idempotency-Key. The optional registered receiver path instead uses callback-v2 signatures and its receiver contract.
  4. Record: the durable attempt outcome drives success, a bounded retry or terminal failure. Inspect task state rather than assuming a lost response means failure.

Delivery is at least once. An uncertain callback can be repeated, so real receivers need durable operation-key deduplication. Cancellation blocks new claims; it cannot undo an in-flight side effect. The optional owner-key redrive path creates a new linked execution with its own funded admission; trial scopes do not grant redrive. Replay an enqueue with the same idempotency key and unchanged body, operation key and schedule; conflicting input returns 409.

Public free-beta registration is enabled. General HTTPS and no-account Connect are enabled for the finite beta. Wallet delegation and credit purchases remain disabled. No price, currency, launch date or automatic top-up is offered. Machine-readable pricing status preserves that distinction.

Information before action.
